# Place Content Workflow Policy

**สถานะ:** ร่าง v0.2 — 29 ก.ค. 2026
**ขอบเขต:** workflow ของ content ประเภท `place` ฝั่ง Collector เท่านั้น

---

## 0. เอกสารนี้คืออะไร

เอกสารกำกับว่างาน place เดินอย่างไรในระบบ — ใช้เป็นเกณฑ์ตัดสินเวลาออกแบบฟีเจอร์ใหม่ เวลารีวิวโค้ด และเวลาเถียงกันว่าพฤติกรรมไหนถูก

**เอกสารนี้เป็นข้อกำหนด ไม่ใช่คำอธิบายสภาพปัจจุบัน** ระบบวันนี้ยังไม่ตรงหลายข้อ ส่วนที่ไม่ตรงคือรายการงานที่ต้องแก้ ไม่ใช่ข้อยกเว้นที่ยอมรับได้ — ดูหมวด 9

ขอบเขตจำกัดที่ `place` โดยตั้งใจ — content type อื่น (`event`, `transport`) มี workflow ของตัวเอง และ**ห้าม**สมมติว่าเหมือนกัน

---

## 1. หลักการพื้นฐาน

หลักหกข้อนี้เป็นรากของกฎทั้งหมดที่เหลือ ถ้ากฎข้อไหนขัดกับหลักเหล่านี้ ให้ถือว่ากฎนั้นผิด

### 1.1 ตำแหน่งเดียว
item หนึ่งตัวอยู่บนบันไดตำแหน่งเดียวเสมอ ตอบได้ทันทีว่า "อยู่ขั้นไหน" โดยไม่ต้องประกอบจากหลายแหล่ง

### 1.2 เดินทีละขั้น
ขึ้นทีละขั้น ลงทีละขั้น ไม่มีการกระโดดข้ามขั้นสำหรับ content workflow — **ไม่มีเครื่องมือของ owner หรือทางลัดใดที่ข้ามขั้นได้**

### 1.3 ถอยไม่ลบ
การถอยกลับ**ไม่ทำลายข้อมูลใดๆ** ของขั้นที่สูงกว่า ทุกอย่างคงอยู่เป็น placeholder ให้ดูและใช้ต่อได้

### 1.4 แก้ค่อยทับ
ข้อมูลถูกเขียนทับเมื่อมีการ**แก้ไขจริง**เท่านั้น การเดินขึ้นซ้ำแล้วทำงานขั้นนั้นใหม่ = ทับของเดิมของขั้นนั้น และ**เฉพาะขั้นนั้น**

### 1.5 gate ไม่ใช่ขั้น
เงื่อนไขที่ต้องผ่านก่อนไปต่อ **เป็นเงื่อนไขที่คำนวณและแสดง ไม่ใช่สถานะ** — แต่ต้องมองเห็นได้เสมอ

### 1.6 ความยากผูกกับสิ่งที่เสีย

| ผลกระทบ | ระดับ |
|---|---|
| ไม่เสียข้อมูล | กดได้เลย |
| เปลี่ยนความรับผิดชอบ / ต้องมีร่องรอย | ต้องใส่เหตุผล |
| กระทบคนอื่น | จำกัด role |
| ทำลายข้อมูลถาวร | ใส่เหตุผล + รหัสผ่าน |

รหัสผ่านใช้เฉพาะขั้นสุดท้ายเท่านั้น ถ้าใส่หลายจุดคนจะพิมพ์อัตโนมัติแล้วมันจะเลิกป้องกันอะไร

## 2. บันไดของ place

### 2.1 ตารางหลัก

| ขั้น | UI | `production_state` | `publication_state` |
|---|---|---|---|
| **1.1** | รับข้อมูลดิบ | `collected` | `draft` |
| **1.2** | คัดข้อมูลส่งเข้า AI | `analyzed` | `draft` |
| **1.3** | สร้างร่างด้วย AI | `generated` | `draft` |
| **1.4** | ตรวจแก้เนื้อหา | `brief_generated` | `draft` |
| **2.1** | ส่งงานไปทำ | `ready_for_content` | `draft` |
| **2.2** | ลงงาน | `field_working` 🆕 | `draft` |
| **2.3** | ตรวจงาน | `field_review` 🆕 | `draft` |
| **3.1** | รับงาน | `writing_assigned` 🆕 | `draft` |
| **3.2** | เขียนบทความ | `writing` 🆕 | `draft` |
| **3.3** | ตรวจและอนุมัติ | `in_review` | `draft` |
| **3.3+** | อนุมัติแล้ว | `ready_for_publish` | `approved` |
| **4** | ส่งเข้า Admin Review | `submitted_for_admin_review` | `approved` |
| **5** | ขึ้น public | `completed` | `published` |

🆕 = ค่าใหม่ที่ต้องเพิ่มเข้า enum

### 2.2 ค่าที่ place ไม่ใช้

- **`content_in_progress`** — ยกเลิกใช้กับ place เพราะกำกวม (2.2 ลงงาน กับ 3.2 เขียนบทความ ต่างก็เป็น "งานกำลังทำ") ยังคงไว้สำหรับ `event` และ `transport`
- **`needs_revision`** — เปลี่ยนเป็น flag ไม่ใช่สถานะ (ดู 2.3)
- **`rejected`** — เปลี่ยนเป็น flag ไม่ใช่สถานะ (ดู 2.3)
- **`unpublished` / `archived` / `deleted`** — อยู่นอกขอบเขตเอกสารนี้ (หลังขึ้น public)

### 2.3 `needs_revision` และ `rejected` เป็น flag ไม่ใช่ขั้น

**เหตุผล:** สถานะสองตัวนี้เป็นที่จอดข้างทาง ไม่ใช่ขั้นบันได เมื่อถอยไปลงที่นั่นระบบจะลืมว่า item ควรอยู่ขั้นไหน ซึ่งขัดกับหลัก 1.1 โดยตรง

**แทนที่ด้วย:** item อยู่ที่ขั้นใดขั้นหนึ่งเสมอ และมี flag ประกอบ

| flag | ความหมาย |
|---|---|
| `revision_requested` | ถูกตีกลับมาให้แก้ ยังไม่ได้เริ่มแก้ |
| `rejected` | ถูกปฏิเสธที่ด่านตรวจ ต้องตัดสินใจว่าจะทำต่อหรือทิ้ง |

ตัวอย่าง: item ที่ไม่ผ่านด่าน 2.3 จะอยู่ที่ **ขั้น 2.2 + flag `revision_requested`** ไม่ใช่ "ขั้น needs_revision"

ผลคือรู้ตำแหน่งเสมอ และเดินขึ้นใหม่ได้โดยไม่ต้องเดาว่าเคยอยู่ไหน

### 2.4 รูปแบบที่ต้องรักษาไว้

**ทุกกระบวนการจบด้วยด่านตรวจของตัวเอง** — 1.4 ตรวจแก้เนื้อหา · 2.3 ตรวจงาน · 3.3 ตรวจและอนุมัติ

กระบวนการใหม่ใดๆ ที่เพิ่มในอนาคตต้องมีด่านตรวจปิดท้ายเช่นกัน

## 3. การเดินหน้า

1. เดินขึ้นได้ทีละขั้นเท่านั้น
2. ข้ามจากกระบวนการหนึ่งไปอีกกระบวนการได้เฉพาะเมื่อ**ผ่านด่านตรวจ**ของกระบวนการเดิม
3. ทุกการเดินหน้าต้องผ่าน gate ของขั้นนั้นครบ
4. **ห้ามมีการเดินหน้าที่เกิดขึ้นเองเป็นผลพลอยได้ของ action อื่น** — ทุกการเลื่อนขั้นต้องมีคนสั่งโดยตั้งใจ

ข้อ 4 มีที่มา: ระบบปัจจุบันมีปุ่ม transition ที่รัน quality แล้วอนุมัติให้อัตโนมัติด้วยค่า `"approve"` ที่ hardcode ไว้ — คนกดคิดว่ากด "ส่งต่อ" แต่กำลังกด "อนุมัติแทนตัวเอง" ไปด้วย พฤติกรรมนี้ผิดหลักข้อนี้

## 4. การถอยหลัง

### 4.1 สองระดับ

| ระดับ | ความหมาย | ผล |
|---|---|---|
| **ถอยในกระบวนการ** | ด่านตรวจขอให้แก้ | กลับไปขั้นก่อนหน้าในกระบวนการเดียวกัน + flag `revision_requested` |
| **ถอยข้ามกระบวนการ** | ตีกลับทั้งชุด | กลับไปด่านตรวจของกระบวนการก่อนหน้า + flag `revision_requested` |

ตัวอย่าง: 3.3 ตีกลับในกระบวนการ → 3.2 · 3.3 ตีกลับข้ามกระบวนการ → 2.3

### 4.2 กฎการถอย

1. **ไม่ลบอะไรทั้งสิ้น** — field pack, ร่าง, deliverable, ไฟล์ที่อัปโหลด ทุกอย่างคงอยู่
2. **ไม่มีเงื่อนไขบล็อกการถอย** — เพราะไม่มีอะไรถูกทำลาย จึงไม่มีเหตุผลต้องกัน
3. ต้อง**ใส่เหตุผล**ทุกครั้ง — เป็นทั้งร่องรอยและ friction ที่ทำให้คิดก่อนกด
4. ถอยแล้วต้อง**เดินขึ้นใหม่ได้เสมอ**

### 4.3 ห้ามมีทางตัน

**ทุกสถานะต้องมีทางออกอย่างน้อยหนึ่งทาง** สถานะที่เข้าได้แต่ออกไม่ได้ถือเป็นบั๊ก ไม่ใช่การออกแบบ

ที่มา: assignment state `closed` ปัจจุบัน**ไม่มีทางออกเลยแม้แต่ทางเดียว** และผู้ใช้เข้าไปอยู่ตรงนั้นโดยไม่ได้ตั้งใจ เพราะมันเกิดเป็นผลพลอยได้ของ action อื่น

## 5. Gate

1. gate **ไม่ใช่สถานะ** — ไม่เก็บลงฐาน คำนวณสดจากข้อมูลจริง
2. gate **ต้องแสดงให้เห็นเสมอ** ทั้งที่ผ่านแล้วและที่ยังไม่ผ่าน
3. เมื่อเดินขึ้นไม่ได้ **ต้องบอกว่าติด gate ตัวไหน** ห้ามตอบเพียงว่าทำไม่ได้
4. **ห้ามกลืน error ที่ทำให้ gate ไม่ผ่าน**

ข้อ 4 สำคัญที่สุด: ระบบปัจจุบันมีจุดที่การสร้าง deliverable ล้มเหลวแล้วถูก catch กลืนทิ้งโดยตั้งใจ ผลคือ item นั้นไม่มีวันผ่านเกณฑ์ publishable source ได้เลย โดยไม่มีใครเห็นสาเหตุ

## 6. บทบาทและสิทธิ์

### 6.1 หลัก
1. สิทธิ์ผูกกับ**เส้นทางเดิน** ไม่ใช่ผูกกับ endpoint
2. ผู้รับผิดชอบ**แยกตามกระบวนการ** — ผู้ลงพื้นที่ (กระบวนการ 2) กับผู้เขียน (กระบวนการ 3) เป็นคนละคน คนละการมอบหมาย
3. ชื่อ guard ต้องตรงกับพฤติกรรม — ปัจจุบันมี `authorizeEditorOrAdmin` ที่ไม่อนุญาต editor

### 6.2 ตารางสิทธิ์
กฎว่า role ไหนเดินเส้นไหนได้ ต้องอ่านได้จากที่เดียว รูปแบบที่กำหนด:

```
{ contentType, from, to, roles, requiresNote, requiresPassword, sideEffects }
```

`contentType` เป็น key บังคับ — ดูหมวด 7.1

## 7. โครงสร้างสถานะ

### 7.1 กฎแยกตาม content type

**เก็บ `production_state` ไว้คอลัมน์เดียวเหมือนเดิม แต่ชุดค่าที่ใช้ได้และกฎ transition แยกตาม content type**

เหตุผล:
- query ข้ามประเภท (คิว, dashboard, listing) ทำงานเหมือนเดิม ไม่ต้องแก้
- บันได place ทำให้ครบและบังคับใช้ได้ โดยไม่ต้องรอออกแบบ event/transport
- ป้องกันไม่ให้ค่าของประเภทหนึ่งหลุดไปใช้กับอีกประเภท ซึ่งเป็นที่มาของค่ากำพร้าที่พบ

สภาพปัจจุบัน: `TRANSITION_RULES` ไม่มี key ของ content type เลย และ `canTransition()` ไม่รับ item หรือ type — กฎชุดเดียวถูกใช้กับทุกประเภท

### 7.2 ความสมบูรณ์ของข้อมูล

1. **การเขียนสถานะต้องผ่านทางเดียว** — ผ่าน repository function เท่านั้น ห้ามยิง SQL ตรง (โค้ด production ปัจจุบันเป็นไปตามนี้แล้ว — ต้องรักษาไว้)
2. **enum ต้องมีนิยามเดียว** — ห้ามมีรายการค่าสถานะมากกว่าหนึ่งชุดในระบบ
3. **แหล่งความจริงมีแหล่งเดียวต่อหนึ่งเรื่อง** — ห้ามเก็บค่าเดียวกันสองที่แล้ว sync เอา ถ้าจำเป็นต้องมีสำเนา ต้องเป็น derived ที่คำนวณสด
4. **ห้ามมี flag ข้ามการตรวจสอบกฎ** — ถ้าต้องมี แปลว่ากฎผิดหรือโมเดลผิด ให้แก้ที่นั่นแทน
5. **การสร้าง item ต้องได้ workflow head พร้อมกันเสมอ** — ต้องอยู่ใน transaction เดียว
6. **แยกการซ่อมออกจากการข้ามขั้น** — เครื่องมือซ่อมข้อมูลที่ไม่ตรงกันเป็นสิ่งที่ต้องมี แต่ต้องแคบ ตรวจสอบได้ และ**ต้องไม่สามารถใช้เลื่อนขั้นงานได้**

## 8. สิ่งที่ห้าม

1. ❌ endpoint ที่ตั้งค่าสถานะเป็นอะไรก็ได้โดยไม่ตรวจกฎ transition
2. ❌ การเลื่อนขั้นที่เกิดขึ้นเองโดยผู้ใช้ไม่ได้สั่ง
3. ❌ การถอยกลับที่ลบข้อมูล
4. ❌ สถานะที่ไม่มีทางออก
5. ❌ ค่าสถานะที่ไม่มี transition ปกติเขียนถึงได้
6. ❌ route ที่ทำงานได้แต่ไม่มีทางเรียกจาก UI (ถ้าตั้งใจให้เป็น API-only ต้องระบุไว้ในเอกสารนี้)
7. ❌ catch ที่กลืน error โดยไม่ log และไม่แจ้งผู้ใช้
8. ❌ การเก็บสถานะเดียวกันไว้สองที่
9. ❌ enum ของสถานะที่นิยามไว้มากกว่าหนึ่งที่

## 9. ระยะห่างจากสภาพปัจจุบัน

รายการนี้คืองานที่ต้องทำเพื่อให้ระบบตรงกับเอกสาร

### 9.1 บั๊กที่ต้องแก้ไม่ว่าจะทำบันไดหรือไม่

| # | อาการ | รายละเอียด |
|---|---|---|
| A | **enum สองชุดไม่ตรงกัน** | `generated` มีใน `repository.mjs` แต่ไม่มีใน `index.mjs` — service เขียนค่านี้ได้ แต่ API ปฏิเสธ item ที่ติดตรงนี้จึงกู้ผ่าน API ไม่ได้ |
| B | **place ไปไม่ถึง `published`** | writer เดียวของ `published` คือ transport-map sync — งาน place ที่ขึ้นเว็บแล้ว Collector ไม่เคยรู้ ค้างที่ `submitted_for_admin_review` ตลอดไป |
| C | **catch กลืน error ตอนสร้าง deliverable** | ทำให้ item ผ่านเกณฑ์ publishable source ไม่ได้ตลอดกาล โดยไม่มีสาเหตุปรากฏ |
| D | **สร้าง item ไม่อยู่ใน transaction** | item เกิดขึ้นโดยไม่มี workflow head ได้ แล้วทุกอย่างหลังจากนั้น throw |

### 9.2 ขั้นที่ยังไม่มีที่ยืน

ต้องเพิ่มค่าใหม่ 4 ค่า: `field_working`, `field_review`, `writing_assigned`, `writing`

กระบวนการ 3 ทั้งกระบวนการแทบไม่มีที่ยืนใน `production_state` เลย — ปัจจุบันถูกติดตามใน assignment state และ article-process แทน

### 9.3 ทางเดินที่ขาด

| ขาด | สภาพปัจจุบัน |
|---|---|
| ขาลงเกือบทั้งหมด | `generated → analyzed` และ `in_review → generated` ไม่มี path |
| ปุ่มของทางถอยที่ปลอดภัย | `reopen` และ `request_changes` ถูกกฎแล้ว แต่ไม่มีปุ่ม |
| ปุ่มถอยหลังส่ง Admin Review | rule อนุญาต แต่ไม่มีปุ่ม |
| `/api/run/clean`, `/api/run/quality` | ไม่มีปุ่ม เป็น API-only |

### 9.4 ของที่ต้องลบหรือยุบ

| รายการ | เหตุผล |
|---|---|
| `PUT /api/items/:id/workflow-model` | ประตูข้ามบันได — **ลบเป็นลำดับสุดท้าย** หลังบันไดครบแล้วเท่านั้น ตอนนี้มันอาจเป็นสิ่งเดียวที่กู้ item ที่ติดค้างได้ |
| `assignment_state` บน workflow head | เก็บซ้ำกับ `content_assignments.state` และแตกกันได้จริง ให้ derive แทน |
| `skip_assignment_transition_validation` | จำเป็นเพราะ mirror สองตัวขัดกัน — หมดความจำเป็นทันทีที่เลิก mirror |
| `skip_production_transition_validation` / `skip_publication_transition_validation` | ไม่มี caller เลย ลบได้ทันที |
| `workflow_status` legacy | ตัดสินว่าตายได้หรือยัง |
| batch endpoint 5 ตัวที่ปิดตาย | `respondBatchReleaseDisabled` |
| assignment state `closed` | ถ้าใช้วงจร revision แทน `closed` จะไม่ถูกสร้างเลย ปัญหาทางตันหายไปโดยไม่ต้องแก้ state machine |

## 10. วินัยการเปลี่ยนแปลง

### 10.1 เพิ่มต้องคู่กับลบ
ทุกงานที่**เพิ่ม**สถานะ เส้นทาง หรือ endpoint ต้องระบุว่า**อะไรถูกแทนที่และลบมันด้วย** ถ้าลบไม่ได้ ต้องเขียนเหตุผลไว้

ที่มา: ระบบสะสม state machine ซ้อนกันห้าชุด เพราะทุกงานถูกสั่งว่า "ทำให้ X ใช้ได้" ไม่เคยมีงานไหนถูกสั่งว่า "ทำ X แล้วเอาของที่มันแทนที่ออก"

### 10.2 ต้องมีทางกดจริง
ฟีเจอร์ไม่นับว่าเสร็จถ้ามีแต่ route — ต้องมี markup และ event binding ที่ผู้ใช้กดถึงได้จริง ถ้าตั้งใจให้เป็น API-only ต้องระบุไว้ในเอกสารนี้

ที่มา: พบ route ที่ไม่มีทางเรียกจาก UI อย่างน้อยห้าตัว รวมถึงขั้นตอนที่อยู่ในเส้นทางหลัก

### 10.3 ลำดับการลงมือ
1. แก้บั๊กในหมวด 9.1 (ไม่ขึ้นกับงานอื่น ทำได้ทันที)
2. เพิ่มค่าใหม่ 4 ค่า + กฎแยกตาม content type
3. เติมขาลงให้ครบทุกขั้น + ปุ่ม
4. ยืนยันว่าไม่มีทางตันเหลือ
5. **แล้วจึง**ลบประตูข้ามบันได

ข้อ 5 ต้องอยู่ท้ายสุดเสมอ — ปิดประตูก่อนบันไดครบ จะเปลี่ยนจาก "ข้ามขั้นได้" เป็น "ติดถาวรกู้ไม่ได้" ซึ่งแย่กว่า
