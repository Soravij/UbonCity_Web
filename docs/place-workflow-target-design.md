# Place Workflow — Target Design

**สถานะ:** ร่าง v0.1 — 29 ก.ค. 2026
**คู่กับ:** `docs/place-workflow-policy.md` (policy บอกว่างานต้องเดินยังไง เอกสารนี้บอกว่าระบบประกอบด้วยอะไร)
**ขอบเขต:** content type `place` ฝั่ง Collector

---

## 0. วิธีอ่านเอกสารนี้

เอกสารนี้ร่างโครงใหม่จากศูนย์ **ไม่ได้ไล่จากสิ่งที่มีอยู่** — ออกแบบว่าระบบ*ควร*ประกอบด้วยอะไร แล้วค่อยจับของเดิมมาเติมลงในช่อง

ผลที่ได้จากการทำแบบนี้: **ของเดิมส่วนใหญ่ใช้ได้ตามเดิม** ปัญหาไม่ได้อยู่ที่ชั้นข้อมูล แต่อยู่ที่ชั้นสถานะ — ดูหมวด 5

---

## 1. หลักคิดข้อเดียว

> ทุกสิ่งในระบบเป็นหนึ่งในสามอย่างเท่านั้น: **ตำแหน่ง** · **ตัวงาน** · **ประวัติ**

| | คืออะไร | มีกี่อันต่อ item |
|---|---|---|
| **ตำแหน่ง** | งานอยู่ขั้นไหนของบันได | **1 เสมอ** |
| **ตัวงาน** | ร่าง, field pack, deliverable, รูป | หลายอัน มีเวอร์ชัน |
| **ประวัติ** | ใครทำอะไรเมื่อไหร่ ทำไม | เพิ่มเรื่อยๆ ไม่เคยแก้ |

ถ้ามีอะไรที่จัดไม่เข้าสามช่องนี้ แปลว่าออกแบบผิด

**สถานะที่เก็บไว้หลายที่ = ตำแหน่งหลายอัน = ผิดหลักข้อนี้** ทุกอาการที่พบในระบบปัจจุบันสืบกลับมาที่นี่ได้หมด

## 2. โครงสร้างห้าชิ้น

### 2.1 ตัวตน (Identity)
`content_item` หนึ่งแถวคืองานหนึ่งชิ้น เกิดตอน import และมี id เดียวตลอดชีวิต

ทุกอย่างที่เหลือผูกกับ id นี้

### 2.2 ตำแหน่ง (Position)
**หนึ่งแถวต่อหนึ่ง item** เก็บเพียง:

| ฟิลด์ | ความหมาย |
|---|---|
| ขั้นปัจจุบัน | ค่าเดียวจากบันได |
| สถานะเผยแพร่ | draft / approved / published |
| flag รอแก้ | ถูกตีกลับมาให้แก้หรือไม่ |
| flag ปฏิเสธ | ถูกปฏิเสธที่ด่านตรวจหรือไม่ |
| เวอร์ชัน + ผู้แก้ล่าสุด | สำหรับ optimistic lock และร่องรอย |

**ห้ามมีอย่างอื่นในนี้** โดยเฉพาะ:
- ❌ ตัวชี้ไปหา artifact (`current_*_id`) — หา artifact ปัจจุบันด้วย query ไม่ใช่ด้วยตัวชี้ที่ต้องคอยดูแล
- ❌ สำเนาสถานะของตารางอื่น (assignment state) — ถ้าอยากรู้ ให้ถามตารางนั้น
- ❌ สถานะ legacy

### 2.3 ตัวงาน (Artifacts)
แต่ละชนิดเก็บ**ทุกเวอร์ชัน** และตอบได้ว่าอันไหนคืออันปัจจุบัน โดย**อนุมานจากข้อมูล ไม่ใช่จากตัวชี้ที่เก็บแยก**

กฎเดียว: **ขึ้นทับ ลงไม่ลบ** — เดินขึ้นแล้วทำงานขั้นนั้นใหม่ = เขียนทับของขั้นนั้น · เดินลง = ไม่แตะอะไรเลย

### 2.4 ประวัติ (History)
ทุกการเปลี่ยนตำแหน่งบันทึกหนึ่งแถว: จากขั้นไหน ไปขั้นไหน ใครสั่ง บทบาทอะไร เหตุผลรหัสอะไร หมายเหตุว่าอะไร เมื่อไหร่

**เพิ่มอย่างเดียว ไม่เคยแก้ ไม่เคยลบ**

ประวัติคือสิ่งที่ทำให้ตอบได้ว่า "ทำไมงานนี้มาอยู่ตรงนี้" ซึ่งเป็นคำถามที่ตอบไม่ได้มาตลอด

### 2.5 กฎ (Rules)
ตารางเดียว หนึ่งแถวต่อหนึ่งเส้นทางที่เดินได้:

```
{ contentType, from, to, roles, requiresNote, requiresPassword }
```

**ความรู้ทั้งหมดว่าใครเดินเส้นไหนได้ อยู่ที่นี่ที่เดียว** ไม่กระจายอยู่ใน middleware, guard, และเงื่อนไขใน handler

ผลพลอยได้: role matrix อ่านได้จากตารางนี้ตรงๆ และ**ทดสอบได้โดยไม่ต้องรันระบบ** ซึ่งเป็นปัญหาตั้งต้นของงานทั้งชุดนี้

## 3. บันได

ตามที่กำหนดใน `place-workflow-policy.md` หมวด 2.1 — 3 กระบวนการ ทุกกระบวนการจบด้วยด่านตรวจของตัวเอง

เดินขึ้นทีละขั้น เดินลงทีละขั้น ลงได้สองระดับ (ในกระบวนการ / ข้ามกระบวนการ)

## 4. Gate

**gate ไม่เก็บ คำนวณสด** — "มี field pack แล้วหรือยัง" ตอบด้วยการถาม ไม่ใช่ด้วยการอ่าน flag ที่ต้องคอยอัปเดต

ผลลัพธ์ที่ gate ต้องคืน: **ผ่าน/ไม่ผ่าน + รายการที่ยังไม่ผ่านเป็นข้อความที่คนอ่านรู้เรื่อง**

ห้ามคืนรายการรหัสสิบเจ็ดตัวแล้วให้คนไปสรุปเอง

---

## 5. แผนที่ของเดิม → โครงใหม่

**หัวใจของเอกสารนี้** — โครงข้างบนไม่ต้องสร้างใหม่เกือบทั้งหมด

### 5.1 ใช้ได้ตามเดิม ไม่ต้องแตะ

| ช่องในโครงใหม่ | ของเดิม | ทำไมใช้ได้เลย |
|---|---|---|
| ตัวตน | `content_items.id` | ถูกออกแบบถูกแล้ว หนึ่งแถวหนึ่งงาน |
| ประวัติ | `workflow_transitions` | **ดีที่สุดในระบบ** — มี from/to/actor/role/reason/note/เวลา ครบ แยกตาม state group เพิ่มอย่างเดียว ตรงตามหมวด 2.4 เป๊ะ |
| ตัวงาน: ร่าง | `content_drafts` + `generation_run_uid` | มีเวอร์ชันถูกต้องแล้ว รอบใหม่ = แถวใหม่ |
| ตัวงาน: การส่งงาน | `content_assignment_submissions` | เพิ่มแถวใหม่ทุกครั้ง ไม่ทับ |
| ตัวงาน: ข้อมูลดิบ | `source_raw_items`, `source_raw_media` | append-only ไม่เคยถูกแก้ — เป็นตาข่ายรองรับสุดท้าย |
| ทางเขียนตำแหน่ง | repository function เดียว | เป็นทางเดียวอยู่แล้ว ไม่มีใครยิง SQL ตรง |
| โครงตารางกฎ | `TRANSITION_RULES` | รูปทรงถูก แค่ต้องเติม key และตัดเส้นทางข้ามขั้น |

### 5.2 ใช้ได้ แต่ต้องปรับ

| ช่อง | ของเดิม | ปรับอะไร |
|---|---|---|
| ตำแหน่ง | `content_workflow_models` | เพิ่มค่าขั้นให้ครบ · เพิ่ม flag สองตัว · **เอาของที่ไม่ควรอยู่ออก** (ดู 5.3) |
| ตัวงาน: field pack | `field_packs` | ทำให้มีเวอร์ชันเหมือนร่าง — ตอนนี้เขียนทับในที่เดิม จึงถอยแล้วของหาย |
| กฎ | `TRANSITION_RULES` | เติม `contentType` · ตัด edge ข้ามขั้นทั้งหมด · เติมเส้นทางขาขึ้นและขาลงให้ครบ |
| การมอบหมายงาน | `content_assignments` | **ลดบทบาทจาก "ที่เก็บสถานะ" เป็น "บันทึกการทำงาน"** — ตำแหน่งของงานอยู่ที่ item ไม่ใช่ที่ assignment |

### 5.3 หายไปจากโครงใหม่

| ของเดิม | ทำไมไม่มีที่ยืน |
|---|---|
| `assignment_state` บน workflow head | ลบแล้วในขั้น 5A — ใช้สถานะของ assignment รอบ active ที่เลือกจาก `content_assignments.state` |
| flag ข้ามการตรวจกฎ | `skip_assignment_transition_validation` ถูกลบพร้อม mirror ในขั้น 5A; flag อื่นตัดสินแยกตาม caller |
| `workflow_status` legacy | สำเนาชุดที่สาม **ผิด 65% ในฐานจริง** |
| `repairWorkflowHeadFromLegacy` | ซ่อมตำแหน่งจากสำเนาที่ผิด 65% — ซ่อมแล้วพังกว่าเดิม |
| article-process | ไม่ใช่สถานะ เป็นมุมมองที่แปะทับสถานะอื่นเพื่อให้เล่าเรื่องรู้เรื่อง พอบันไดชัดแล้วไม่ต้องมีตัวแปล |
| `current_draft_id` | ตัวชี้ที่**ไม่เคยถูกเซ็ตเลย (0 จาก 52)** และตัวอ่านทุกตัวหา draft ล่าสุดเองอยู่แล้ว |
| `current_field_pack_id`, `current_review_report_id` | ทำงานถูกต้อง 100% แต่ผิดหลัก "ตำแหน่งเก็บแต่ตำแหน่ง" — **เอาออกทีหลัง ไม่เร่ง** เพราะไม่ได้ก่อปัญหา |
| เส้นทางข้ามขั้นในตารางกฎ | บันไดที่อนุญาตให้ข้ามไม่ใช่บันได |
| endpoint ตั้งค่าสถานะอิสระ | ประตูข้ามบันได — **เอาออกท้ายสุด** หลังบันไดครบและไม่มีทางตันเหลือ |

### 5.4 ต้องสร้างใหม่จริงๆ

รายการนี้สั้นกว่าที่คาด:

1. **ค่าขั้นใหม่ 4 ค่า** — `field_working`, `field_review`, `writing_assigned`, `writing`
2. **คอลัมน์ flag 2 ตัว** — รอแก้ / ปฏิเสธ (ตั้งชื่อไม่ให้ชนกับ `content_assignments.state`)
3. **เวอร์ชันของ field pack**
4. **ตัวคำนวณ gate ที่คืนข้อความอ่านรู้เรื่อง**
5. **ปุ่มขาลงทุกขั้น** — เส้นทางส่วนหนึ่งมีกฎรองรับแล้ว แค่ไม่มีปุ่ม

**ไม่มีตารางใหม่ ไม่มีการย้ายข้อมูล ไม่มีการเขียนใหม่จากศูนย์**

## 6. ทำไมงานถึงเล็กกว่าที่กลัว

แยกระบบเป็นสองชั้นแล้วดู:

| ชั้น | สภาพ |
|---|---|
| **ชั้นข้อมูล** — ตัวงานและประวัติ | **ถูกต้องเกือบทั้งหมด** ร่างมีเวอร์ชัน การส่งงานเพิ่มแถว ข้อมูลดิบไม่เคยถูกแตะ ประวัติบันทึกครบ ยกเว้น field pack ตัวเดียว |
| **ชั้นสถานะ** — ตำแหน่งและกฎ | **นี่คือที่ที่ปัญหาทั้งหมดอยู่** สำเนาสามชุด กฎที่อนุญาตให้ข้าม ประตูข้ามบันได มุมมองที่แปะทับ |

งานที่ต้องทำจึงเป็นการ**จัดชั้นสถานะให้เรียบ** ไม่ใช่การรื้อระบบ — ชั้นข้อมูลที่ถูกต้องอยู่แล้วคือสิ่งที่ทำให้การถอยหลังปลอดภัยได้ตั้งแต่แรก

และเป็นเหตุผลว่าทำไมกฎ "ถอยไม่ลบ" ถึงทำได้จริง ไม่ใช่ความหวัง

## 7. ลำดับที่โครงนี้แนะนำ

ต่างจากการไล่แก้ทีละบั๊ก — ลำดับนี้ไล่ตามชั้น จากล่างขึ้นบน

| # | ทำอะไร | เหตุผล |
|---|---|---|
| 1 | ปิดของที่ทำลายข้อมูลได้ | `repairWorkflowHeadFromLegacy` เขียนทับตำแหน่งจากสำเนาที่ผิด 65% |
| 2 | ซ่อมชั้นข้อมูลจุดเดียวที่พลาด | field pack ให้มีเวอร์ชัน — หลังจากนี้ "ถอยไม่ลบ" เป็นจริงทุกขั้น |
| 3 | ทำให้ตัวอ่านพังดัง | ~19 จุดที่ตกหายเงียบเมื่อเจอค่าที่ไม่รู้จัก ทำก่อนเพิ่มค่าใหม่ |
| 4 | จัดชั้นสถานะ | เพิ่มค่าและ flag · เติม edge ให้ครบ · ตัด edge ข้ามขั้น · เติม `contentType` |
| 5 | เลิกทำสำเนา | 5A เสร็จแล้ว: เอา `assignment_state` mirror และ `skip_assignment_transition_validation` ออก; 5B เหลือ `workflow_status` legacy |
| 6 | เติมปุ่ม | ทุกเส้นทางที่มีกฎแล้วต้องกดได้จริง |
| 7 | ยืนยันไม่มีทางตัน | เดินทุกขั้นขึ้นและลงบนฐานทดสอบ |
| 8 | ปิดประตูข้ามบันได | **ท้ายสุดเสมอ** ปิดก่อนบันไดครบ = เปลี่ยนจากข้ามขั้นได้เป็นติดถาวร |

ข้อ 1 กับ 2 ไม่ขึ้นกับอะไรเลย เริ่มพร้อมกันได้
